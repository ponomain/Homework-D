## 1. Задача

Написать консольную утилиту, которая упаковывает **плоскую папку** (только файлы, без подпапок) в один архивный файл собственного формата **SARC** и распаковывает его обратно.

Требования, которые определили устройство кода:

- Работать **потоком**: память не должна зависеть от размера файлов.
- Файлы `.txt` обязаны быть корректным **UTF-8**, иначе упаковка или распаковка отклоняется.
- Целостность содержимого проверяется **CRC32**.
- Битый, обрезанный или вредоносный архив **не должен оставлять мусор** и не должен писать за пределы целевой папки.
- Понятные сообщения об ошибках (`ArchiveException`) и коды возврата консоли.

Использование:

```
pack   <папка> <архив>
unpack <архив> <папка>
```

Коды возврата: `0` успех, `1` ошибка упаковки или распаковки, `2` неверные аргументы.

## 2. Формат архива

```
┌──────────┬─────────┬───────────────────────────────┬─────────┐
│ "SARC"   │ версия  │ запись 1 │ запись 2 │ ... N   │ маркер  │
│ 4 байта  │ 1 байт  │                               │ 0 (1 б) │
└──────────┴─────────┴───────────────────────────────┴─────────┘

запись = тип(1) | длина имени(2) | имя(N) | размер(8) | содержимое(размер) | CRC32(4)
```

| Поле | Размер | Значение |
|---|---|---|
| Сигнатура | 4 байта | `53 41 52 43`, то есть ASCII `SARC`. По ней отличаем наш архив от чужого файла |
| Версия | 1 байт | Сейчас `1` |
| Тип записи | 1 байт | `1` текст (`.txt`, проверяется UTF-8), `2` бинарный, `0` маркер конца |
| Длина имени | 2 байта | Беззнаковое число, максимум 65535 |
| Имя | N байт | Имя файла в UTF-8, без пути |
| Размер | 8 байт | Длина содержимого в байтах |
| Содержимое | `размер` байт | Файл как есть |
| CRC32 | 4 байта | Контрольная сумма **содержимого** |
| Маркер конца | 1 байт | `0` на месте типа: записей больше нет |

Все числа хранятся в порядке **big-endian** (старший байт первым). Записи идут в порядке возрастания **байтов имени**, поэтому один и тот же набор файлов всегда даёт побайтно одинаковый архив.

Главное свойство формата: **длину каждого поля сообщает предыдущее поле**. Длина имени говорит, сколько байт читать под имя; размер говорит, сколько байт содержимого. Парсеру не нужны разделители и возврат назад.

## 3. Пример: 53 байта по полям

Папка `in/` содержит два файла:

```
in/
  a.txt   текст «Да»        (2 символа, 4 байта)
  b.bin   байты 01 02 03    (3 байта)
```

Архив, который получается из неё (снят с настоящего `Packer`):

```
0000  53 41 52 43 01 01 00 05 61 2e 74 78 74 00 00 00
0010  00 00 00 00 04 d0 94 d0 b0 b7 53 00 3a 02 00 05
0020  62 2e 62 69 6e 00 00 00 00 00 00 00 03 01 02 03
0030  55 bc 80 1d 00
```

| Смещение | Поле | Байты | Расшифровка |
|---|---|---|---|
| 0–3 | сигнатура | `53 41 52 43` | `SARC` |
| 4 | версия | `01` | формат версии 1 |
| **запись 1: a.txt** | | | |
| 5 | тип | `01` | текст, проверяется UTF-8 |
| 6–7 | длина имени | `00 05` | 5 байт |
| 8–12 | имя | `61 2e 74 78 74` | `a.txt` |
| 13–20 | размер | `00 00 00 00 00 00 00 04` | 4 байта (символов всего 2) |
| 21–24 | содержимое | `d0 94 d0 b0` | `Да`: «Д» = `d0 94`, «а» = `d0 b0` |
| 25–28 | CRC32 | `b7 53 00 3a` | сумма по этим 4 байтам |
| **запись 2: b.bin** | | | |
| 29 | тип | `02` | бинарный, UTF-8 не проверяется |
| 30–31 | длина имени | `00 05` | 5 байт |
| 32–36 | имя | `62 2e 62 69 6e` | `b.bin` |
| 37–44 | размер | `00 00 00 00 00 00 00 03` | 3 байта |
| 45–47 | содержимое | `01 02 03` | как есть |
| 48–51 | CRC32 | `55 bc 80 1d` | сумма по этим 3 байтам |
| **конец** | | | |
| 52 | маркер конца | `00` | записей больше нет |

Что здесь важно увидеть:

- **Символы и байты разные вещи.** «Да» это 2 символа, но 4 байта. В поле размера лежит `4`.
- **Размер идёт до содержимого, а CRC после.** Размер известен заранее (`Files.size`), а CRC можно посчитать только когда содержимое уже прошло через поток.
- **Ноль в позиции типа означает конец.** Поэтому типы записей начинаются с 1.

## 4. Устройство кода

```text
Main  (аргументы, коды возврата)
├── Packer.pack      (папка → архив)
│     └── вызывает StreamIo.copyExactly
└── Unpacker.unpack  (архив → папка)
      └── вызывает StreamIo.copyExactly

StreamIo.copyExactly  (ровно N байт)
├── Utf8Validator     (UTF-8 по кускам, только для .txt)
└── CRC32 из JDK      (контрольная сумма)

Format (константы) и ArchiveException (ошибки)
используют Packer, Unpacker и StreamIo.
```

| Класс | Роль |
|---|---|
| `Format` | Константы формата: сигнатура, версия, типы, маркер, размер буфера (32 КиБ), лимит имени (65535) |
| `ArchiveException` | Единое исключение с сообщением `[файл] проверка '…' не пройдена: …`. Наследует `IOException` |
| `StreamIo` | `copyExactly`: переносит ровно N байт между потоками, считая CRC и проверяя UTF-8. Общая для упаковки и распаковки |
| `Utf8Validator` | Потоковая строгая проверка UTF-8, умеет склеивать символ, разрезанный границей буфера |
| `Packer` | Упаковка: `pack`, `collect` (список файлов), `writeEntry` (одна запись) |
| `Unpacker` | Распаковка: `unpack`, `readArchive`, `readEntry`, защита имён, `commit` с откатом |
| `Main` | Разбор аргументов командной строки |

## 5. Флоу pack

```text
pack(папка, архив)
 1. Проверить: вход является папкой, архив не лежит внутри неё
 2. collect: только обычные файлы, имя не длиннее 65535 байт
 3. Отсортировать записи по байтам имени
 4. Создать temp-файл .sarc-*.tmp рядом с архивом
 5. Записать SARC и версию
 6. Для каждого файла: writeEntry
 7. Записать маркер конца (0)
 8. Закрыть потоки (сброс буфера на диск)
 9. ATOMIC_MOVE: temp → архив

 Ошибка на шагах 1–2  → ArchiveException, на диске ничего нет
 Ошибка на шагах 4–9  → удалить temp-файл и пробросить исключение
```

`writeEntry` для одного файла:

```text
writeEntry(файл)
 size = Files.size
   → тип → длина имени → имя → размер
   → copyExactly: файл → архив (считает CRC, проверяет UTF-8)
   → in.read() == -1 ?   (файл не вырос во время упаковки)
   → utf8.finish()       (только для .txt)
   → CRC32
```

Почему именно так:

- **Временный файл рядом с архивом**: перенос внутри одной файловой системы выполняется одной операцией. Читатель никогда не увидит наполовину записанный архив, а старый архив при неудаче остаётся нетронутым.
- **`collect` до создания temp-файла**: если какой-то файл не подходит (подпапка, слишком длинное имя), падаем до того, как что-то записано.
- **Заголовок записи уходит в архив раньше проверки содержимого**: если в `.txt` окажется битый UTF-8, запись уже начата. Это нормально именно потому, что пишем во временный файл.

## 6. Флоу unpack

```text
unpack(архив, папка)
 1. Создать целевую папку и staging (.sarc-unpack-*) внутри неё
 2. readArchive: проверить сигнатуру и версию
 3. Цикл по записям. Прочитать тип:
      1 или 2             → readEntry (файл пишется в staging), снова в начало цикла
      0 (маркер конца)    → выйти из цикла
      иное / конец потока → ArchiveException
 4. После маркера не должно быть ни байта, иначе ArchiveException
 5. commit: проверить, что ни одно имя не занято в целевой папке
 6. commit: перенести файлы из staging (move без перезаписи)
      ошибка на середине → откат: удалить уже перенесённые файлы
 7. finally: удалить staging (и при успехе, и при любой ошибке)
```

`readEntry` для одной записи:

```text
readEntry
 1. readN(2)   длина имени       → 0: ошибка «пустое имя»
 2. readN(N)   имя               → строгий UTF-8
 3. validateName                 → нет '/', '\', NUL, '.', '..'
 4. имя уже встречалось?         → ошибка «дубликат»
 5. readN(8)   размер            → отрицательный: ошибка
 6. создать файл в staging       (CREATE_NEW)
 7. copyExactly: архив → файл    (считает CRC, проверяет UTF-8)
 8. readN(4)   CRC из архива     → не совпал с посчитанным: ошибка CRC32
 9. names.add(имя)               запись принята
```

Почему именно так:

- **Staging внутри целевой папки**: перенос в конце является быстрым переименованием, а не копированием.
- **Сначала всё проверяем, потом публикуем**: битый архив не оставляет в целевой папке ни одного файла.
- **Два прохода в `commit`**: сначала проверка, что ни одно имя не занято, потом перенос без перезаписи. Если в середине случился сбой, перенесённые файлы удаляются.
- **Защита имён в два слоя**: `validateName` отвергает опасные символы, `safeResolve` проверяет, что итоговый путь является прямым потомком папки.
- **Память не зависит от заявленного размера**: размер из заголовка не используется для выделения памяти. Если он ложный, поток просто закончится раньше (ошибка «обрыв данных»).

## 7. Как читаются поля

Разбор идёт **строго последовательно, за один проход, без возврата назад**. На примере из раздела 3:

| Шаг | Функция | Читает | Байты |
|---|---|---|---|
| 1 | `readArchive` | `readN(in, 5)`: сигнатура и версия | 0–4 |
| 2 | `readArchive` | `in.read()`: тип записи | 5 |
| 3 | `readEntry` | `readN(in, 2)`: длина имени | 6–7 |
| 4 | `readEntry` | `readN(in, 5)`: имя | 8–12 |
| 5 | `readEntry` | `readN(in, 8)`: размер | 13–20 |
| 6 | `readEntry` → `copyExactly` | содержимое кусками, пишет в staging | 21–24 |
| 7 | `readEntry` | `readN(in, 4)`: CRC | 25–28 |
| 8 | `readArchive` | `in.read()`: тип второй записи, повтор шагов 3–7 | 29–51 |
| 9 | `readArchive` | `in.read()` = `0`: маркер, затем `in.read()` = `-1` | 52 |
| 10 | `commit` | поток не читает, работает с файлами в staging | |

Упаковка зеркальна: `writeEntry` пишет те же поля в том же порядке. Роли `copyExactly` при этом меняются (`in` это файл, `out` это архив), но сама функция об этом не знает.

Какая функция читает что:

- **`readN`** короткие поля фиксированной длины (и имя). Если байт меньше нужного, архив оборван.
- **`copyExactly`** содержимое: длина может быть любой, поэтому идёт кусками по 32 КиБ, без накопления в памяти.
- **Тип записи** читается обычным `in.read()`: нужно отличить маркер конца (`0`) от конца потока (`-1`), это разные ошибки.

## 8. Краткая теория по I/O на примерах из задачи

### 8.1. Поток, а не файл целиком

`InputStream` и `OutputStream` дают доступ к данным **последовательно**: прочитал кусок, обработал, прочитал следующий. Файл на гигабайты проходит через буфер в 32 КиБ, и память не растёт. В задаче это `StreamIo.copyExactly`.

Альтернатива `Files.readAllBytes` загружает файл в память целиком, и для больших файлов это либо медленно, либо падает с `OutOfMemoryError`.

### 8.2. `read` может вернуть меньше, чем просили

```java
int n = in.read(buf, 0, 32768);   // n может быть 1, 100, 32768 или -1
```

- `n > 0` прочитано `n` байт (не обязательно все запрошенные);
- `n == -1` конец потока.

Поэтому чтение ведётся **в цикле** (`while (left > 0)` в `copyExactly`), а для коротких полей используется `readNBytes(n)`, который сам повторяет чтение до нужной длины или до конца потока. Тестовый `TrickleInputStream` отдаёт по 1–3 байта за вызов и проверяет, что код это выдерживает.

### 8.3. Буферизация

Каждое обращение к диску дорого. `BufferedOutputStream` и `BufferedInputStream` накапливают данные в памяти и отправляют порциями. В задаче заголовки пишутся по 1, 2 и 8 байт: без буфера это были бы тысячи мелких обращений. Буфер обязательно сбрасывается при закрытии потока, поэтому перенос архива (`ATOMIC_MOVE`) делается **после** закрытия.

### 8.4. Байты и символы

Файл это байты. Символы появляются, когда байты **декодируют** в кодировке. UTF-8 кодирует символ 1–4 байтами: латиница 1, кириллица 2, эмодзи 4.

- Длина имени и размер в формате считаются **в байтах**, а не в символах.
- Корректность UTF-8 проверяется `CharsetDecoder` с режимом `REPORT`: плохие байты вызывают ошибку. По умолчанию (`REPLACE`) они молча превратились бы в `�`, и проверка ничего не проверяла бы.
- Границы буфера могут разрезать символ пополам. `Utf8Validator` хранит недочитанный хвост между вызовами, а в конце файла вызывается `finish()`, чтобы поймать обрыв посередине символа.

### 8.5. Двоичные числа

`DataOutputStream` (запись) и `ByteBuffer` (чтение) умеют работать с числами `short`, `int`, `long` в порядке big-endian.

```java
out.writeShort(5);                       // 00 05
int len = buf.getShort() & 0xFFFF;       // 0..65535 вместо знакового значения
```

`byte` в Java знаковый (−128…127). Чтобы получить 0…255, делают `b & 0xFF`. По этой же причине имена сортируются через `Arrays.compareUnsigned`.

### 8.6. Закрытие ресурсов

Поток держит дескриптор операционной системы и буфер. Его нужно закрыть, даже если случилась ошибка:

```java
try (InputStream in = Files.newInputStream(path)) {
    ...
}   // закроется автоматически, в любом случае
```

Правило владения: кто открыл, тот закрывает. Поэтому `Unpacker.unpack(InputStream, Path)` поток **не закрывает**, а `unpack(Path, Path)` закрывает, потому что сам его открыл.

### 8.7. Файлы и пути (NIO.2)

| Что нужно | Чем сделано в задаче |
|---|---|
| Открыть поток | `Files.newInputStream`, `Files.newOutputStream` |
| Список папки | `Files.list` (его `Stream` надо закрывать) |
| Не перезаписать существующий файл | `StandardOpenOption.CREATE_NEW`, `Files.move` без `REPLACE_EXISTING` |
| Не идти по символическим ссылкам | `LinkOption.NOFOLLOW_LINKS` |
| Безопасный путь | `dir.resolve(name).normalize()` и проверка `getParent()` |
| Атомарная публикация файла | `Files.move(tmp, target, ATOMIC_MOVE)` |
| Временные файлы | `Files.createTempFile`, `Files.createTempDirectory` |

### 8.8. Контрольная сумма

`CRC32` из `java.util.zip` считается **по мере прохождения данных**: `crc.update(buf, 0, n)` после каждого прочитанного куска. Сумма обнаруживает случайные повреждения, но не защищает от умышленной подмены. Для этого нужна криптографическая подпись.

### 8.9. Исключения

`IOException` проверяемое: компилятор требует его обработать или объявить. `ArchiveException` наследует его, поэтому ошибки формата и ошибки диска идут одним путём до `Main`. Правила, которые соблюдены в коде:

- Сообщение называет файл или запись и сбойную проверку, а не просто «ошибка».
- При ошибке сначала **убираем за собой** (удаляем temp и staging), потом пробрасываем исключение.
- Ошибка во время уборки не должна подменять исходную причину: в `commit` она добавляется через `addSuppressed`, в `deleteQuietly` игнорируется.
- Причина сохраняется в `cause`, чтобы стек не терялся.

## 9. Обработка ошибок и гарантии

| Ситуация | Что происходит |
|---|---|
| Вход `pack` не папка, подпапка или ссылка внутри | `ArchiveException`, архив не создаётся |
| Имя файла длиннее 65535 байт | `ArchiveException` при упаковке |
| `.txt` с битым UTF-8 | `ArchiveException` при упаковке и при распаковке |
| Файл изменился во время упаковки | `ArchiveException` («обрыв» или «стал больше»), temp удалён |
| Неверная сигнатура или версия | `ArchiveException` в начале разбора |
| Архив оборван или нет маркера конца | `ArchiveException`, целевая папка пуста |
| Лишние байты после маркера | `ArchiveException` |
| Неверный CRC | `ArchiveException` с ожидаемым и полученным значением |
| Имя с `/`, `\`, `..`, NUL | `ArchiveException` («безопасность имени») |
| Дубликат имени, в том числе по регистру | `ArchiveException` |
| Имя допустимо для формата, но не для файловой системы (больше 255 байт) | `ArchiveException` с причиной от файловой системы |
| Файл с таким именем уже есть в целевой папке | `ArchiveException`, ничего не распаковано, существующие файлы целы |
| Сбой на середине `commit` | Откат: перенесённые файлы удаляются |

Гарантии:

1. Битый или подложный архив не оставляет в целевой папке ничего.
2. Существующие файлы никогда не перезаписываются.
3. Имя из архива не может вывести запись за пределы целевой папки.
4. Память не зависит от размера файлов и от заявленных в архиве размеров.
5. При ошибке упаковки старый архив с тем же именем остаётся нетронутым.

## 10. Тесты

Класс `ArchiverTest` (около 45 тестов, JUnit 5, `@TempDir`). Вспомогательные классы:

- `ArchiveBuilder` собирает архивы **вручную**, байт за байтом. `Packer` всегда пишет корректный архив, а для проверки реакции `Unpacker` на *неправильный* нужен генератор неправильных (неверный CRC, отрицательная длина, лишний байт).
- `TrickleInputStream` отдаёт по 1–3 байта за `read`, проверяя частичные чтения и разрезанные символы UTF-8.

| Группа | Что проверяют |
|---|---|
| Нормальные случаи | Пустой архив, пустые файлы, кириллица и эмодзи, символ на границе буфера, все 256 значений байта, файл 200 КБ |
| Порядок | Сортировка по байтам UTF-8, а не по символам Java |
| Ошибки `pack` | Битый UTF-8, подпапка, старый архив сохраняется, нет temp-мусора |
| Разбор заголовков | Сигнатура, версия, тип, длина, CRC, дубликаты, лишние байты, нет маркера |
| Безопасность | `../evil.bin`, разделители, `..`, NUL, имя длиннее 255 байт, конфликт `A.bin` и `a.bin` |
| UTF-8 в содержимом | Оборванная последовательность, overlong, суррогат, код выше U+10FFFF, ошибка далеко за первым буфером |
| Откат и уборка | Второй файл битый, первый не появляется; staging удаляется и при успехе, и при ошибке |
| Повреждения | Архив обрезается на каждой длине; инвертируется каждый байт по очереди |
| Консоль | Коды возврата 0, 1, 2 |

Два теста зависят от файловой системы: проверка регистронезависимых дубликатов пропускается на системах, чувствительных к регистру, а проверка лимита 65535 байт в имени на Windows пропускается всегда (система не даёт создать такое имя).

## 11. Запуск

Тесты:

```
mvn test
```

Консольная утилита (после сборки классов):

```
java -cp target/classes org.getmentor.homework.io.Main pack   in/ out.sarc
java -cp target/classes org.getmentor.homework.io.Main unpack out.sarc restored/
```

Если `mvn` и `java` не в `PATH`, нужно указать `JAVA_HOME` (JDK 25) и использовать Maven из IntelliJ IDEA.

## 12. Известные ограничения

- Только плоские папки: подпапки и символические ссылки отклоняются.
- Между проверкой файла и его чтением есть небольшое окно, в котором файл может измениться. Ловится только изменение размера.
- Откат в `commit` «лучший из возможных»: при сбое питания или вмешательстве другого процесса часть файлов может остаться.
- CRC32 защищает от случайных повреждений, но не от умышленной подмены.
- В сообщении `Main` при исключении без текста выводится `Ошибка: null`.
